# カナリークラウド代替：Store階層＋全社ダッシュボード設計案

2026-08-22 作成。カナリークラウド（月40万円・8アカウント）依存を解消するための、tama-fudosan-crm-2026の拡張設計。**まだ実装・DB反映はしていない、レビュー用の案。**

## 前提として確認した事実

- カナリー実機（flat-agency社、SS Trust社、名岐不動産アカウント経由）を限定的にスクリーンショット確認済み（個人情報は見ていない・保存していない）。
- カナリーの顧客一覧＝実質的な受信トレイ（最新のやりとり順、ステータス・タグ・反響元列、ビュー切替タブ）。1店舗だけで顧客3,363〜7,804件規模。
- 現行`crm-project-new`の`Organization`モデルは単一店舗の平坦なフィールド（`storeName`等1個ずつ）で、店舗という概念が無い。加えて`User`は組織に1:1紐付けなので、社内オペレーターが複数クライアントを横断して見る仕組みも無い。

### 訂正：カナリーにも「まとめ画面」は存在する

前回の調査で「カナリー自身にも社を横断する一覧は無い」と結論づけたが、**誤りだった**。`console.cloud.canary-app.com/management/<key>/...` という別URL体系（`管理画面`）が存在し、以下を実機で確認した：

- 見出し「顧客一覧 / 株式会社名岐不動産」で、**同じ会社の複数店舗の顧客が1つの一覧に統合表示**され、「**担当店舗**」列（例：ピタットハウス名古屋駅北店）で判別できる。
- ヘッダー右上のドロップダウンで、担当しているテナントslugを切り替えられる（例：asahi-fudousan, asahi-fudousan-digk, -fuchu, -hgs, -hongo, -izms, -kita, -mnm, -oizg, -tkok...）。会社をまたいだ切替に見える。
- ドロップダウン内に「店舗追加＋」「一括ログイン」というメニューもある。
- ログインは店舗別アカウント（`mcp-canary`のcanary-config.jsonにある8組の店舗別credential）とは**別の、スタッフ個人に紐づく管理者アカウント**（実機では「西野あすか」名義）。

つまりカナリーの実際の構造は：

```
スタッフ個人の管理アカウント（例：西野あすか）
  └ ドロップダウンで担当テナントを切替
      └ テナントA（1社・複数店舗の統合顧客一覧、担当店舗列あり）
      └ テナントB
      └ ...（そのスタッフが担当している範囲だけ）
```

これは今回設計した`StaffOrgAccess`（Userが複数Organizationにアクセスできる中間テーブル）の方向性と一致する。**「一括ログイン」の中身と、このアカウントが42社全部を見れるのか担当分だけなのかは未確認**（個人情報保護のため深追いしていない）。

## ギャップ（このために新規に必要なもの）

| # | ギャップ | 影響範囲 |
|---|---|---|
| 1 | Store（店舗）エンティティが無い | 定休日・営業時間・テンプレートが会社単位でしか持てない |
| 2 | 定休日ルールが曜日＋第◯週＋祝日の複合条件を表現できない | 店舗別振り分け判定ができない |
| 3 | `organization.findFirst()`が17箇所（cron/webhook/settings） | 2社目を追加した瞬間に壊れる |
| 4 | 反響メールの宛先で会社を判別する仕組みが無い | 42社分の反響を1つのwebhookで受けても会社を特定できない |
| 5 | Userが1組織に1:1固定 | 社内オペレーターが担当する複数クライアントを横断して見れない |
| 6 | メッセージ単位の意図分類が無い | 「この質問には希望条件を聞き返す」等の打ち手ガイドが実装できない |
| 7 | 顧客の返信有無・意欲シグナルを表すフィールドが無い | 自動アポ組ロジック・優先対応リストの入力に使えない |
| 8 | 物件の空室状態フラグが無い | 満室時の即代替提案（全社共通の勝因、+28〜54pt）ができない |

## 全社ダッシュボードの画面設計

既存の `/inbox`（今は自組織のみ・`user.organizationId`で絞り込み）を拡張する形。カナリーの「管理画面」で確認した構造をほぼそのまま踏襲する。

- `user.isStaff = true` の場合：`staffAccess`に登録された全組織の顧客を横断表示（新規反響＝`最新のやりとり`降順、カナリーの顧客一覧と同じ並び）
- 一覧の列に「**会社名・担当店舗**」を追加（カナリー管理画面の「担当店舗」列と同じ役割。横断表示なので必須）
- ヘッダーに会社/テナント切替ドロップダウン（カナリーの実装と同じ位置・同じ挙動）。「すべて」を選べば42社横断、特定の会社を選べば1社の複数店舗まとめ、さらに店舗を選べば1店舗だけ、と3段階で絞り込める
- クリックすると顧客詳細へ
- クライアント側ユーザー（`isStaff = false`）は今まで通り自組織のみ・切替ドロップダウンは表示しない

## 統合コンポーザー（メール・LINE・SMS共通エディタ）

**カナリーの弱点**：メール・LINE・SMSがそれぞれ別エディタで、チャンネルを切り替えるたびにUIごと変わり操作が煩雑。ここはカナリーを真似ず、改善する。

### 設計方針

1つの「送信パネル」コンポーネントを作り、**チャンネルはプルダウン/タブで選ぶだけ、入力欄・変数挿入・定型文選択・送信ボタンは共通**にする。裏側の送信APIだけチャンネルごとに分岐する（既存の`src/app/api/send-message`が近い役割を持つはずなので、そこを拡張する形）。

チャンネルごとの制約はエディタの外側（入力補助・警告表示）で吸収する：

| 制約 | メール | LINE | SMS |
|---|---|---|---|
| 文字数上限 | 実質無制限 | 実質無制限（画像等はメッセージ種別が変わる） | 全角670字/1通（Twilio分割送信） |
| 件名 | あり | なし | なし |
| 添付ファイル | あり | 画像/ファイル送信は別API | 基本不可（URL誘導） |
| 開封トラッキング | あり（Resend） | 既読は取れるが「開封」の概念とは別（LINE公式仕様） | 無し |
| リッチ表現 | HTML | LINEの装飾記法 | プレーンテキストのみ |

実装イメージ：
- 入力欄は共通の1つ。チャンネルをLINE/SMSに切り替えたら「件名欄」を隠す、文字数カウンターを表示、HTML装飾ボタンを無効化、といった**UIの出し分け**で対応する（別画面を作らない）。
- 定型文・変数（`{{customer_name}}`等）は共通のテンプレートDBから同じ形式で挿入できるようにする（現状`AgentTemplate`と`Template`が二重構造になっている問題は、この統合を機に整理する）。
- 送信履歴（`Message`モデル）はチャンネル問わず同じ一覧（会話ビュー）に時系列で並べる。これは既存の`Message.channel`フィールドで既に対応できている。

### 他社の統合エディタから借りるパターン（調査済み）

同じ課題（メール/SMS/LINE/チャット統合）を解決している既存ツールを調べたところ、共通して以下のパターンが使われている：

- **Front**：非同期（メール）と同期（チャット/SMS）でコンポーザーの「モード」自体を変えている。メールは書式設定・添付・開封トラッキングONOFFがあるフルエディタ、SMS/チャットはメッセージバブル型の軽量入力欄。→ うちも「メール＝フルエディタ／LINE・SMS＝チャット型」の2モードに倒すのが良さそう（件名や装飾ボタンを条件表示するより、モードごとレイアウトを変える方がシンプル）
- **Intercom**：SMS送信時、コンポーザー内に文字数と**分割セグメント数をリアルタイム表示**（「670字超えたら2通に分かれます」を先に見せる）。これはそのまま真似したい。
- **HubSpot Conversations / Re:lation（国産）**：同一顧客の複数チャンネルのやり取りを1本の時系列スレッドに自動統合。これは`Message.channel`があるので設計上すでに対応できている。Re:lationは「未対応/保留/対応完了/対応不要」の4ステータス＋二重対応防止ロック機能を持つ。**二重対応防止（誰かが今この顧客を見ている表示）**はカナリーにもある機能で、42社を1画面で捌く体制では特に重要——`/inbox`の設計に追加を検討したい。

## 実務ノウハウ（反響対応playbook）からの反映

### 現状のモデルで対応できている

- **追客の途中停止**：`WorkflowRun`の`STOPPED_BY_REPLY`は「返信が来たら追客ロジックを切り替える」という核心原則と整合済み

- **電話結果の記録**：`CustomerRecord.callResult`が既にある

### 機能・UI追加（スキーマ以外）

- **NG定型の送信前警告**：「また機会がありましたら」等の"引き"表現は非成立側に多い（最大−26pt）。統合コンポーザーの送信前チェックとして検出・警告する
- **日程二択のクイック挿入**：意欲シグナル検出時に「具体的な日時を二択提示」が勝ち筋。候補日時2つを自動整形して挿入するボタンを設ける
- **希望条件ヒアリングの促し**：費用・条件への回答後に希望条件を聞き返せているかをチェックし、`WishCondition`未入力のまま送信しようとしたら軽く促す

### 未確認（推測に留めた点）

- 店舗別に「勝ち筋」が異なるかどうかは、読んだ4ファイルには会社単位の比較しかなく確認できなかった。店舗差の有無は別途確認が必要

## いい生活(e-bukken)との役割分担

`docs/e-bukken-sfa-playbook.md`を読んだ結果、**tama-fudosan-crm-2026側に重複実装すべきではない**という結論になった。

- いい生活からの反響取込・返信自動化は、既存の`e-bukken-sfa-agent-design.md`（拡張＋中央agent方式）が正本。Auth0のBearerトークン必須・React SPAのDOM構造依存という技術的制約があり、CRM側で作り直すとAuth0セッション管理とDOM解析ロジックを二重に持つことになる。**CRMはAPI経由でデータを受け取る消費側に徹する**（e-bukken側の問い合わせAPI提供有無は未確認）
- いい生活の内蔵AI返信機能（月400回上限）とは競合せず棲み分ける。ヘヤクレスの価値は夜間の即応と有人対応の品質であり、独自AI返信機能を作るとしても「いい生活のAI機能がカバーしない時間帯・案件」の補完に限定する
- 年間追客登録数の上限（プラン制約）はいい生活への増枠相談で解決する運用課題であり、CRM側の設計問題ではない

### 自動返信の設計に活かす点

`docs/market-research/auto-reply-playbook.md`（競合の自動返信メール2,138通を分析したベンチマーク）から、**「何をすると機械的だと見抜かれるか」のリストがそのまま自社の自動返信の反面教師になる**：

- 「担当者より改めてご連絡させていただきます」型の"予告だけ"文面は避ける
- 自動返信でも実質回答（空室可否・初期費用の具体額）を含める設計にする（他社が回答を入れないのは技術的制約であり、差別化の機会）
- テンプレート変数（顧客名/屋号/送信者公開名/初回反響物件/LINEボタン/来店予約ボタン等）の変換コード設計はe-bukken方式を流用し、統合コンポーザーのテンプレ変数体系に組み込む
- チャネルは顧客の連絡先登録状態で自動的に決まる（メール/LINE/SMS/マイページ）という設計思想は、統合コンポーザーのチャネル選択UIにそのまま反映する

## S-FIT案件（Toggle）からの参考

Itaruが業務委託で設計しているS-FIT案件（不動産会社向け電話タスク・メッセージAI自動化、Toggle Holdings経由）の資料を読み、同じ発想（トリガー×SLA・意図分類）がより練られた形で実装されていたため転用できる点を反映した。

**前提の訂正**：当初「T-01〜T-08フル仕様・意図カテゴリ辞書そのもの」を参照するつもりだったが、それらは「12月リリース版」という別ファイル（未提供）にあり、今回読めたのは「10月末リリース版」の資料。以下は10月末版の実装済み実例からの抽出。

### Workflow/SLAモデルの拡張

S-FITのSLA体系は`基準日時（商談作成日・ステージ変更日・内見日等）+ オフセット（日/時刻）+ 曜日/繁忙期補正 + 生成除外条件 + 未完了ならループ再生成`という形。現行`Workflow`の日数オフセット型ドリップ設計では「時刻指定」「営業日/繁忙期補正」「条件不成立時のみループ」を表現できない。加えて「定期ルール（停滞2日でTEL等）」と「即時ルール（申込意思・内見リクエストは即時タスク化）」の2階建て設計が明言されており、`WorkflowTrigger`を**周期型／イベント即時型**の2種類に分けるモデルが有効（実装は今回踏み込まない、次回検討）。

### セルフ予約は「自動確定」ではなく「リクエスト→承認」にする

S-FITの「顧客自走化モデル」（3原則：探すはAI・決めるは人／楽しさは決める理由の手段／透明性が信頼をつくる）では、内見予約は自動確定ではなく**リクエスト→営業承認（SLA目安30分）**の形。現行`StoreVisitBooking`は`status`フィールドを持つが、承認フローとして明示的に設計されていない。tama-fudosan-crm-2026のセルフ予約もこの承認制に倣うべき。

### テンプレ自動選定パターン（チョイスCRM研究）

物件状況3分岐（内見可/退去予定/一番手あり/募集終了）×経過日数×通信手段（架電あり/なし）でテンプレを自動選定する設計。`InquiryProperty.vacancyStatus`（今回追加済み）と組み合わせて、テンプレ選定ロジックの参考にできる。

### 決定：自動送信の範囲は段階導入（2026-08-26 Itaru指示）

S-FITはあえて「ダッシュボードを持たない」「AIは下書きまで、送信は必ず営業（人）」という設計にしている。理由は①宅建業法上の説明責任は人が負う、②文面事故の構造的防止、③現場が把握していない提案が届くと対応が噛み合わなくなる、の3点。

これを踏まえてtama-fudosan-crm-2026の方針が決まった：

- **Phase 1（当面）：下書き承認方式**。AI/自動判定は下書き（返信文・タグ・振り分け先の推奨）を生成するところまで。送信・タグ付け・確定操作はオペレーターが手動で行う。既存の`inquiry-agent`拡張（下記）と同じ「ガイド方式」をCRM全体の初期設計原則にする。
- **Phase 2（軌道に乗ってから）：完全自動送信へ移行**。オペレーターの信頼が積み上がった機能から順に自動化する（全機能を一度に自動化しない）。

`Organization.autoReplyEnabled`は当面「下書き生成トリガー」として使い、送信ボタンを人が押す運用にする。完全自動送信への切替は機能単位でフラグを分けられる設計にしておく（例：`autoReplyMode: "DRAFT_ONLY" | "AUTO_SEND"`）。

## 既存エージェント（inquiry-agent）の埋め込み計画

Itaruから、**既に開発済みの「対応店舗判断エージェント」（`inquiry-agent`拡張、旧名flat-agency-router）の機能をtama-fudosan-crm-2026に埋め込みたい**という指示があった。実物（`heyacules-ai`リポジトリ`inquiry-agent/`、originのmainブランチに存在）を読んだ内容を反映する。

### これは何か

フラットエージェンシーの「物件なし・エリア不明」反響に対し、定休日ルールに基づく一次対応店の推奨と、初回メール／LINE／社内コメントの下書きを生成するChrome拡張。カナリー顧客ページにパネルを注入して動く。

### 設計思想がPhase 1の方針とそのまま一致している

READMEに明記されている通り、**推奨・下書きを出すだけで、送信もタグ付けも人間が手動で行う「ガイド方式」**（自動書き込みは一切しない）。全ての自動検出項目に人間による上書きが効く。これは今回決定したPhase 1の「下書き承認方式」の実例そのもの。

### 技術的に埋め込みやすい設計になっている

`router.js`（判定エンジン）と`drafts.js`（下書き生成）は**Node・ブラウザ両対応の純粋関数**として書かれており、DOMに依存しない（`content.js`だけがブラウザ専用でカナリーのDOMを読む部分）。つまりtama-fudosan-crm-2026（Next.js）にモジュールとしてほぼそのまま移植できる。移植時にDOM読み取り部分（`content.js`相当）を、CRM自身のCustomer/Messageレコードから直接読む処理に置き換えるだけで済む。

### Store振り分けロジックの実例（StoreClosedDayRule設計の裏付け）

`router.js`の実装は、今回設計した`StoreClosedDayRule`（曜日＋第◯週＋祝日＋臨時休業）とほぼ同じ構造で店舗の営業日を判定していた（実データで裏付けが取れた）。加えて、店舗振り分けの判定木は優先順位付きルールの連鎖になっている：

```
対応不要物件リスト該当 → 終了
マンスリー/シェアハウス短期 → 全店LINE通知
テナント/事務所利用 → 全店LINE通知
受験生（大学名＋受験文脈、季節条件あり） → 特定店舗固定
対応言語（英/中/韓） → 特定店舗固定
元付が特定店舗 → その店舗
物件指定あり → 外部システム（いい生活）参照を案内（自動連携はしない）
店舗名の記載あり → その店舗
（該当なし） → 全店舗へフォールバック通知
```

この「上から先勝ちのルールチェーン」パターンは、42社それぞれの振り分けロジックが違うことを踏まえると、**汎用DBルールテーブルとして今すぐ完全に一般化するより、会社ごとのルールをコード（設定ファイル）として持つ現行方式を当面維持し、パターンが出揃ってから共通エンジン化する方が安全**（推測：42社分をいきなり1つの巨大な条件分岐エンジンにすると保守性が落ちる）。

### テンプレートの第3の重複ソースが見つかった

`drafts.js`は`mailJP(name)`のようなハードコードされた関数でテンプレート文を生成している。これは`Template`・`AgentTemplate`（前回指摘した二重構造）に続く**3つ目の別々のテンプレート置き場**。inquiry-agentをCRMに統合する際、このテンプレートも統合コンポーザーのテンプレートDBに正式に移行する。
